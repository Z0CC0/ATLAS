For a small project, use **Postgres**. Switch to Redis only when your job volume actually requires it.

**Why Postgres fits a small project**

- **It can handle the load.** A queue built on `SELECT ... FOR UPDATE SKIP LOCKED` copes with roughly a thousand jobs per minute. A small project will rarely get close to that.
- **The job and its data are in one transaction.** You enqueue the job inside the same transaction as the write it depends on. If that write is rolled back, the job is rolled back too, so a job can never start for data that doesn't exist.
- **Jobs survive crashes without extra setup.** The queue is stored in the database, so if the process dies, the jobs are still there when it comes back.
- **There's no new service to manage.** You're already running Postgres.

**What Redis would cost you**

Redis handles much higher volume and has lower latency, under a millisecond. The downside is that it's one more service to run, monitor and upgrade. You also have to set up persistence yourself: if AOF isn't enabled, a restart loses every job in the queue. That's a real risk for a queue, and it's easy to miss.

**When to switch**

Move to Redis if you start regularly going past about a thousand jobs per minute, or if sub-millisecond latency starts to matter. Until then, Postgres is simpler and safer.
