I wouldn't. Keep integrity rules in the database and put business logic in the application, behind a single entry point.

The upside is real: no application path can skip the rule, not even a script run by hand.

The costs:

Triggers are invisible to anyone reading the application code. A change that looks simple can fire other triggers, with no trace.

Your team's current test tools don't cover them. You need tests that run against a real database.

Debugging is worse. An error inside a trigger shows up as a failed write and doesn't say which rule caused it.

Migrations become fragile, because trigger order matters and isn't declared anywhere.

What to do instead: keep only the integrity rules in the database (constraints, foreign keys, uniqueness and domain checks). Put the business logic in the application, behind a single entry point. That gives you the same guarantee as a trigger, **as long as direct database access is reserved to migrations**.
