internal knowledge

I wouldn't put all of it there. Keep integrity rules in the database and business logic in the application, behind a single entry point.

The upside is real: no application path can skip the rule, not even a script run by hand. But it costs you in four places:

Triggers are invisible to anyone reading the application code. A change that looks simple can fire other triggers and leave no trace.

Your team's current testing tools won't cover them. You need tests that run against a real database.

Debugging gets harder. An error inside a trigger shows up as a failed write and doesn't say which rule caused it.

Migrations become fragile, because trigger order matters and nothing records it.

A better split: the database keeps only what protects integrity, meaning constraints, foreign keys, uniqueness and domain checks. The business logic goes in the application, and every change goes through one entry point.

That entry point gives you the **same guarantee as a trigger, as long as direct database access is reserved for migrations**.
