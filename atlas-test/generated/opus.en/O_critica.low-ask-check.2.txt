I wouldn't put all of it in triggers. Keep integrity rules in database, business logic in application behind single entry point.

Your instinct has real upside: no application path can skip a trigger, not even a script someone runs by hand.

Cost comes with it, though. Nobody reading application code sees triggers, so a change that looks simple can fire others and leave no trace.

Your team's current test tools won't cover them. You'd need tests running against a real database.

Debugging gets worse. When a trigger fails, you just see a failed write, with nothing saying which rule caused it.

Migrations get fragile, because trigger order matters and nothing declares it.

**Alternative:** keep in database only what protects integrity: constraints, foreign keys, uniqueness, domain checks. Put business logic in application, behind one entry point that every write goes through.

That entry point gives same guarantee as triggers, **as long as direct database access stays reserved to migrations**. Hand-run scripts must go through entry point too, or they bypass it.
