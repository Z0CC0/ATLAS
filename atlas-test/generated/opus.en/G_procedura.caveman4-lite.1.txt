Don't run `ALTER TABLE ... ALTER COLUMN ... TYPE` directly. It rewrites the whole table while holding an `ACCESS EXCLUSIVE` lock. With ten million rows, your service stays down until the rewrite finishes.

Instead, add a new column next to the old one and switch over in these steps, in this order:

1. **Check the data.** Count the rows in `colonna` that are not all digits. Any row that is not all digits will fail to convert. Fix those rows before you go on.
2. **Add the new column.**
   ```sql
   ALTER TABLE t ADD COLUMN colonna_int integer;
   ```
3. **Fill it in batches of 10,000 rows.** Small batches mean no long lock is held on the table.
4. **Add a trigger** that keeps `colonna` and `colonna_int` in step. Rows written while the migration runs then stay correct.
5. **Ship a code change** that reads from `colonna_int`.
6. **Only after that, drop the old column.**
   ```sql
   ALTER TABLE t DROP COLUMN colonna;
   ```

Step 6 is irreversible. Once you drop the column, the only way to get that data back is a restore from backup. Before you run it, make sure the new code is live and reading from `colonna_int`.
