Don't use a direct `ALTER TABLE t ALTER COLUMN colonna TYPE integer`. That command rewrites the whole table while holding an `ACCESS EXCLUSIVE` lock. On ten million rows, your service is down until the rewrite finishes. Instead, move the data to a new column in stages:

**1. Check that every value converts.** Count the rows that are not all digits:
```sql
SELECT count(*) FROM t WHERE colonna !~ '^[0-9]+$';
```
If the count is not 0, fix those rows before you continue.

**2. Add the new column:**
```sql
ALTER TABLE t ADD COLUMN colonna_int integer;
```

**3. Fill the new column in batches of 10,000 rows.** Small batches mean no long lock is held on the table. Repeat until no rows are left to fill.

**4. Add a trigger that keeps the two columns in step during the migration.** New writes to `colonna` then also reach `colonna_int`.

**5. Change the code to read from `colonna_int`, and ship it.**

**6. Only after that, drop the old column:**

> **Warning:** This step cannot be undone. After the column is dropped, the data comes back only through a restore from backup. Before you run it, make sure step 5 is live and working.
> ```sql
> ALTER TABLE t DROP COLUMN colonna;
> ```

Steps 1 to 5 keep the old column untouched, so you can still back out up to that point. Step 6 is where you can no longer back out.
