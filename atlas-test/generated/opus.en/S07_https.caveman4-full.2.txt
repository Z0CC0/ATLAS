HTTPS is ordinary HTTP sent through a channel that TLS encrypts. Before any HTTP is sent, the client and server run a TLS handshake to set up that channel.

**Handshake**

1. The client opens the connection and lists the TLS versions and ciphers it supports.
2. The server picks one version and one cipher. It also sends its certificate.
3. The client checks the certificate. A certificate binds a domain name to a public key, and a certificate authority (CA) signs it. The client follows the chain of signatures up to a root certificate it already holds. If the chain reaches a trusted root, the certificate is accepted.
4. Client and server agree on a session key. Today this is usually done with an elliptic curve Diffie-Hellman (ECDHE) exchange.

**Why a symmetric session key**

Asymmetric encryption is too expensive for real traffic. It is used only during setup, and the actual data is encrypted with the faster symmetric session key.

**After the handshake**

All traffic is encrypted and authenticated. Anyone in the middle can't read it, and they can't change it without being detected.

**TLS 1.3 vs 1.2**

The TLS 1.3 handshake takes one round trip. TLS 1.2 needs two, so TLS 1.3 connections start faster.

**Common misconception**

A certificate says nothing about who runs the site. It only says that the domain controls that key. A phishing site with a valid certificate still gives you an encrypted connection, but it's an encrypted connection to the phishing site.
