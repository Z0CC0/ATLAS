Usually no. On a column with only three distinct values, the database normally won't use a B-tree index. Each value matches a large share of the table. When a filter selects more than roughly 5-10% of the rows, the planner picks a sequential scan over the index.

You still pay for the index even when it goes unused. Every insert, update, and delete has to maintain it, and it takes up disk space.

There is one exception. If one of the three values is rare and you query for it often, create a partial index on that value only. That index works well:

```sql
CREATE INDEX orders_failed_idx ON orders (status) WHERE status = 'failed';
```

The index stays small. Writes for the common values don't touch it. The planner uses it for queries that filter on the rare value.
