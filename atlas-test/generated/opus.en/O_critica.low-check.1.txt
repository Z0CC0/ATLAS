I wouldn't put all of it there. Keep integrity rules in the database and business logic in the application.

The upside you're after is real. No application path can skip a trigger, not even a script someone runs by hand.

The costs:

Anyone reading application code can't see triggers. A change that looks simple can fire others and leave no trace.

Your team's current test tools won't cover them. You'd need tests running against a real database.

Debugging gets harder. An error inside a trigger shows up only as a failed write, with no sign of which rule caused it.

Migrations become fragile, because trigger order matters and nothing declares it.

**Alternative:** keep in the database only what protects integrity: constraints, foreign keys, uniqueness and domain checks. Put the business logic in the application, behind a single entry point. That entry point gives you the same guarantee as a trigger, **as long as direct database access is reserved for migrations**.
