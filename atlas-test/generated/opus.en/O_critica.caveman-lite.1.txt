I wouldn't put all of it in triggers. The guarantee you want is real, but you can get it more cheaply another way.

**What you gain:** no application path can skip the rule. That includes a script someone runs by hand.

**What it costs you:**
- **Hidden behavior.** Nobody reading the application code can see triggers. A change that looks simple can fire other triggers and leave no trace.
- **Testing.** Your team's current test tools won't cover triggers. You'll need tests that run against a real database.
- **Debugging.** An error inside a trigger shows up only as a failed write. It doesn't say which rule caused it.
- **Migrations.** Trigger order matters, but nothing declares that order. Migrations become fragile as a result.

**What I'd do instead:** split the work by its purpose.
- **Database:** keep only what protects integrity: constraints, foreign keys, uniqueness and domain checks.
- **Application:** put the business logic here, behind a single entry point that every write goes through.

That single entry point gives you the same guarantee as the trigger, with one condition: only migrations get direct access to the database. If you enforce that rule, nobody can bypass the logic, and it stays visible, testable and debuggable.
