Don't convert the column in place. Add a new integer column, move the data across in stages, and drop the old column only at the end.

A direct `ALTER TABLE ... ALTER COLUMN ... TYPE integer` rewrites the whole table while holding an `ACCESS EXCLUSIVE` lock. On ten million rows, the service would be down for as long as the rewrite takes.

Do these steps in this order:

1. Check that every existing value can be converted. Count the rows that aren't all digits:
   ```sql
   SELECT count(*) FROM t WHERE colonna !~ '^[0-9]+$';
   ```
   Fix those rows before you go any further.

2. Add the new column:
   ```sql
   ALTER TABLE t ADD COLUMN colonna_int integer;
   ```

3. Fill the new column in batches of 10,000 rows so no long lock is held on the table.

4. Add a trigger that keeps the two columns in step while the migration runs.

5. Change the code to read from `colonna_int` and ship it.

6. Only after that, drop the old column:
   ```sql
   ALTER TABLE t DROP COLUMN colonna;
   ```

**Step 6 can't be undone.** Once the column is dropped, the only way to get the data back is to restore from a backup. Don't run it until the code reading `colonna_int` is working in production.
