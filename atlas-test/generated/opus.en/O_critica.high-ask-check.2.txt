I wouldn't put all of it there. Keep integrity rules in the database and business logic in the application.

The upside is real: no application path can skip the rule, not even a script run by hand.

The costs:

Triggers can't be seen from the application code. A change that looks simple fires others and leaves no trace.

Your team's current test tools don't cover them. You need tests that run against a real database.

Debugging gets harder. An error inside a trigger shows up as a failed write and doesn't say which rule caused it.

Migrations get fragile. Trigger order matters, and nothing records it.

What I'd do instead: keep only the integrity rules in the database (constraints, foreign keys, uniqueness, domain checks). Put the business logic in the application, behind a single entry point. That entry point gives the same guarantee as a trigger, as long as direct database access is reserved for migrations.
