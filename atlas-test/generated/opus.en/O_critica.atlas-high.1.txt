I wouldn't put **all** of it in triggers. Keep integrity rules in the database and business logic in the application.

The upside is real: no application path can skip a trigger, not even a script run by hand.

The costs:

Triggers are invisible to anyone reading the application code. A change that looks simple can fire others and leave no trace.

Your team's current test tools don't cover them. You'd need tests that run against a real database.

Debugging is harder. An error inside a trigger shows up only as a failed write and doesn't say which rule caused it.

Migrations become fragile. Trigger order matters, and nothing declares it.

The alternative: keep only integrity rules in the database (constraints, foreign keys, uniqueness, domain checks). Put the business logic in the application, behind a **single entry point**. That gives the same guarantee as triggers, as long as you reserve direct database access for migrations.
