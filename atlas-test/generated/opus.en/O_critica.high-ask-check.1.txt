I'd advise against putting all of it in triggers. Keep integrity rules in the database, and put business logic in the application behind one entry point.

The upside is real: no application path can skip a trigger, not even a script someone runs by hand.

The costs:

Anyone reading the application code can't see triggers. A change that looks simple can set off others and leave no trace.

Your team's current test tools don't cover triggers. You'd need tests that run against a real database.

Debugging gets harder. An error inside a trigger shows up only as a failed write and doesn't say which rule caused it.

Migrations become fragile. Trigger order matters, and nothing declares it.

The alternative is to split the work by type of rule. The database keeps what protects integrity: constraints, foreign keys, uniqueness and domain checks. The application holds the business logic behind a **single entry point**. That entry point gives the same guarantee as a trigger, **as long as direct database access is reserved for migrations**.
