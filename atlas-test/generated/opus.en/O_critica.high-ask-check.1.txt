I wouldn't put all of it there. Keep integrity rules in the database and business logic in the application.

The upside is real: no application path can skip the rule, not even a script someone runs by hand.

The costs:

Triggers are invisible to anyone reading the application code. A change that looks simple can fire other triggers, and nothing records that it happened.

Your team's current test tools can't cover them. The tests have to run against a real database.

Debugging gets harder. An error inside a trigger comes back as a failed write, with no sign of which rule caused it.

Migrations become fragile, because trigger order matters and nothing declares it.

The alternative: keep in the database only what protects integrity, meaning constraints, foreign keys, uniqueness and domain checks. Put the business logic in the application, behind **one entry point**.

That entry point gives the same guarantee as a trigger, **but only if direct database access is limited to migrations**.
