internal knowledge

HTTPS: plain HTTP carried inside a channel that TLS encrypts. Before any page moves, client and server run a handshake:

1. Client opens connection, lists TLS versions and ciphers it supports.

2. Server picks a version and a cipher, sends back its certificate.

3. Client checks certificate. Certificate binds a domain name to a public key and carries a signature from a certificate authority. Client verifies that signature by walking the chain up to a root certificate it already holds.

4. Both sides agree on a session key, today typically through an elliptic curve Diffie-Hellman exchange.

Session key symmetric, because asymmetric encryption costs too much for real traffic. Asymmetric part only sets things up; symmetric key carries the data.

From then on, traffic encrypted and authenticated: anyone in the middle can neither read it nor modify it.

TLS 1.3 cuts the handshake to a single round trip, against two in TLS 1.2, so connections start faster.

One common misreading: certificate says **nothing about who runs the site**. It says only that the domain controls that key. A valid padlock on a scam domain still means an encrypted connection to the scammer.
