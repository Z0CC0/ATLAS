HTTPS is ordinary HTTP carried inside a channel that TLS encrypts. Before any HTTP is sent, client and server run a handshake to set that channel up:

1. The client opens the connection and lists the TLS versions and ciphers it supports.

2. The server picks a version and a cipher from that list and sends back its certificate.

3. The client checks the certificate. A certificate binds a domain name to a public key and is signed by a certificate authority. The client verifies that signature by following the chain of signers up to a root certificate it already holds.

4. Client and server agree on a session key. Today this is usually done with an elliptic curve Diffie-Hellman exchange.

The session key is symmetric because asymmetric encryption costs too much to use on real traffic. Once the key is agreed, all traffic is encrypted and authenticated. Anyone in the middle can neither read it nor change it.

TLS 1.3 cuts the handshake down to a single round trip. TLS 1.2 needs two.

A valid certificate says nothing about who runs the site. It proves **only that the domain controls that key**.
