internal knowledge

HTTPS is HTTP running inside a channel that TLS encrypts.

The handshake runs in this order:

1. The client opens the connection and lists the TLS versions and ciphers it supports.
2. The server picks a cipher and a version, then sends its certificate.
3. The client checks the certificate's signature by following the chain up to a root certificate it already has.
4. Client and server agree on a session key, these days usually through an elliptic curve Diffie-Hellman exchange.

The certificate links a domain name to a public key. A certificate authority signs it.

The session key is symmetric because asymmetric encryption costs too much to use on real traffic.

After the handshake, all traffic is **encrypted and authenticated**. Nobody in the middle can read it or change it.

TLS 1.3 needs only one round trip for the handshake. TLS 1.2 needs two.

The certificate does **not** say who runs the site. It says only that whoever controls the domain also controls that key.
