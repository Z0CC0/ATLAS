Usually not. A plain B-tree index on a column with only three distinct values normally goes unused. Each value matches a large share of the table. Once a filter selects more than roughly 5–10% of the rows, the planner decides a sequential scan is cheaper than going through the index, so it skips the index.

The index still has costs even when nothing uses it. Every insert, update and delete has to maintain it, and it takes up disk space.

**The exception** is when one of the three values is rare and that's the value you query for. In that case a partial index that covers only the rare value works well:

```sql
CREATE INDEX orders_pending_idx ON orders (id) WHERE status = 'pending';
```

The index stays small because it only holds the rare rows, and queries filtering on `status = 'pending'` can use it because they select only a small fraction of the table.

So skip a plain index on that column. If you often look up a rare value, add a partial index for that value.
