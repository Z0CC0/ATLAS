I wouldn't put all of it in triggers. Put integrity rules in the database and business logic in the application.

**What you gain:** the benefit is real. No application path can skip the rule, not even a script someone runs by hand.

**What it costs:**
- **Hidden behavior.** People reading the application code can't see triggers. A change that looks simple can fire other triggers and leave no trace.
- **Testing.** Your team's current test tools don't cover triggers. You'd need tests that run against a real database.
- **Debugging.** An error inside a trigger shows up only as a failed write. Nothing says which rule caused it.
- **Migrations.** They become fragile. Trigger order matters, and nothing declares that order.

**What I'd do instead:**
- Keep only integrity protection in the database: constraints, foreign keys, uniqueness and domain checks.
- Keep the business logic in the application, behind a single entry point.
- Allow direct database access only for migrations. With that rule in place, the single entry point gives the same guarantee as a trigger: nothing can skip it.

You keep the protection you want and avoid the hidden behavior, the testing gap, the debugging trouble and the fragile migrations.
