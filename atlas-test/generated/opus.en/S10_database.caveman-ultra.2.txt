**Pick Postgres. Start with Postgres alone.** Postgres handles all four workloads acceptably, though none outstandingly. Orders need real transactions, and Postgres gives them. That requirement is not negotiable.

**Options by workload:**

- **Orders:** Postgres or MySQL are equivalent here. MySQL is weaker on data types and complex queries, so it loses overall. MongoDB got multi-document transactions late, and they cost. ClickHouse does not fit: point updates are its weak spot.
- **Catalogue:** MongoDB's variable schemas make this easier. That gain does not justify giving up cheap transactions on orders.
- **Text search:** Postgres built-in search is good enough below 1 million documents and weak above. Elasticsearch is far better on relevance, synonyms and typo tolerance. Elasticsearch is not an authoritative store. Another database must feed it, and Elasticsearch cannot replace that database.
- **Analytics:** Postgres carries tens of millions of rows, then scans get slow. ClickHouse is far better here, with columnar scans orders of magnitude ahead.

**Where this usually ends up:** Postgres as the authoritative store, with Elasticsearch and ClickHouse fed from it. Do not build that on day one. Each added system brings a synchronisation problem and a data alignment problem. The real cost is not the licence. The real cost is the time of the people who keep each system running.

**When to add each one:**

- **Elasticsearch:** add it when the catalogue passes about 1 million documents, or when search quality measurably fails. Below 1 million documents, adding it is almost always premature.
- **ClickHouse:** add it when analytics reach tens of millions of rows and you can measure the scans getting slow.
- **Rule:** add a system only when a specific workload demands it, with numbers in hand.
