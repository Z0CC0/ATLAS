HTTPS is ordinary HTTP carried inside a channel that TLS encrypts. The web requests and responses are the same as always. The difference is that everything travels through a protected tunnel, and that tunnel is set up at the start of every connection.

**1. The client says hello.** Your browser opens the connection and lists the TLS versions and ciphers it supports.

**2. The server answers and identifies itself.** The server chooses one version and one cipher from that list. It also sends back its certificate.

**3. The browser checks the certificate.** A certificate links a domain name to a public key, and a certificate authority signs it. Your browser checks that signature by following the chain of signers upward until it reaches a root certificate it already has. If the chain ends at a root it trusts, the certificate is accepted.

**4. Both sides agree on a session key.** Today this is usually done with an elliptic curve Diffie-Hellman exchange. The session key is symmetric, meaning the same key encrypts and decrypts. Asymmetric encryption would be too slow and expensive to use on all the real traffic, so it's only used to set up the connection.

**5. The protected conversation begins.** From here on, all traffic is encrypted and authenticated. Anyone sitting between you and the server can't read it and can't change it without being detected.

**Speed:** TLS 1.3 finishes this setup in a single round trip between client and server. TLS 1.2 needed two, so new connections start faster.

**What the padlock doesn't tell you:** A valid certificate proves only that whoever controls the domain also controls that key. It says nothing about who runs the site or whether they can be trusted. A phishing site can have a perfectly valid certificate for its own domain. HTTPS guarantees that you're talking privately to that domain, not that the domain is honest.
