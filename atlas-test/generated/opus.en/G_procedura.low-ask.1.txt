Don't run `ALTER TABLE t ALTER COLUMN colonna TYPE integer` directly. It rewrites the whole table while holding an ACCESS EXCLUSIVE lock, so the service is down for the entire rewrite. Instead, migrate in stages:

1. Check that every existing value can be converted by counting the rows that are not all digits. If the count is not zero, deal with those rows before going further.

   ```sql
   SELECT count(*) FROM t WHERE colonna !~ '^[0-9]+$';
   ```

2. Add the new column.

   ```sql
   ALTER TABLE t ADD COLUMN colonna_int integer;
   ```

3. Fill the new column in batches of ten thousand rows, so that no long lock is held on the table.

4. Add a trigger that keeps the two columns in step for as long as the migration runs, so rows written or changed during the backfill are not missed.

5. Change the application code to read from `colonna_int`, and ship it.

6. Only after the new code is live and working, drop the old column.

   ```sql
   ALTER TABLE t DROP COLUMN colonna;
   ```

**Step 6 can't be undone.** Once the column is dropped, its data comes back only through a restore from backup. Until then you can go back to the old column at any point, so don't drop it until you're sure the new one is right.
