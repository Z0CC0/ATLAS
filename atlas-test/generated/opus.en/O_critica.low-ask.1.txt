I wouldn't put all of it in triggers. Keep only integrity rules in the database and put business logic in the application, behind a single entry point.

The upside you want is real. With triggers, no application path can skip the rule, not even a script someone runs by hand.

The cost is high:

Anyone reading the application code can't see triggers. A change that looks simple can fire other triggers and leave no trace.

Your team's existing test tools don't cover them. You'd need tests that run against a real database.

Debugging gets harder. An error inside a trigger shows up as a failed write, with nothing saying which rule caused it.

Migrations become fragile. Trigger order matters, and nothing declares it.

The alternative is to split the work. The database keeps what protects integrity: constraints, foreign keys, uniqueness and domain checks. The business logic goes in the application, and every write passes through one entry point.

That entry point gives you the same guarantee as a trigger, as long as only migrations get direct database access. That condition is what actually makes the rule impossible to bypass, so enforce it on purpose.
