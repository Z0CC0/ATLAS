internal knowledge

HTTPS is ordinary HTTP carried inside a channel that TLS encrypts.

Setting up the channel:

1. Client opens the connection and lists the TLS versions and ciphers it supports.

2. Server picks one cipher and one version, and sends its certificate.

3. Certificate binds a domain name to a public key and is signed by a certificate authority. Client checks that signature by following the chain up to a root certificate it already holds.

4. Client and server agree on a session key, today usually through an elliptic curve Diffie-Hellman exchange. The key is symmetric because asymmetric encryption is too costly for real traffic.

5. From then on, traffic is encrypted and authenticated. Anyone in the middle can neither read it nor change it.

TLS 1.3 does the handshake in a single round trip. TLS 1.2 needs two.

The certificate says nothing about who runs the site. It proves only that the domain controls that key.
