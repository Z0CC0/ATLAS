Don't run `ALTER TABLE ... ALTER COLUMN TYPE` directly. It rewrites the whole table while holding an `ACCESS EXCLUSIVE` lock, so your service is down for the entire rewrite. Do the migration in steps instead:

1. **Check that every value converts.** Count the rows whose value is not all digits. If the count is not zero, fix those rows before you start.

2. **Add the new column.**
   ```sql
   ALTER TABLE t ADD COLUMN colonna_int integer;
   ```

3. **Fill the new column in batches of 10,000 rows.** Small batches never hold a long lock on the table, so traffic keeps flowing.

4. **Add a trigger that keeps the two columns in step.** Rows written during the migration then land in `colonna_int` too.

5. **Change the code to read from `colonna_int`, and ship it.** Make sure the new code works in production before the last step.

6. **Only then, drop the old column.**

> **Warning:** Step 6 is irreversible. Once you drop the column, the data comes back only through a restore from backup. Run this only after the new code is live and confirmed working.
> ```sql
> ALTER TABLE t DROP COLUMN colonna;
> ```

You can undo steps 1 to 5 because the old column still holds the original data. Step 6 is the only point of no return.
