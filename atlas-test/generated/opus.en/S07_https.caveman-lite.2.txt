HTTPS is ordinary HTTP sent through a channel that TLS encrypts. TLS builds that channel with a short handshake before any HTTP data moves.

**1. Hello.** The client opens the connection. It lists the TLS versions and ciphers it supports.

**2. Server reply.** The server picks one version and one cipher from that list. It also sends its certificate.

**3. Certificate check.** A certificate binds a domain name to a public key. A certificate authority (CA) signs it. To check the signature, the client follows the chain of signers up to a root certificate it already has. If the chain ends at a trusted root, the client accepts that the key belongs to that domain.

**4. Session key.** Client and server then agree on a shared session key. Today this is usually done with an elliptic curve Diffie-Hellman exchange. The session key is symmetric because asymmetric encryption is too expensive for real traffic. Asymmetric cryptography is used only to set up the connection. After that, fast symmetric encryption carries the data.

**5. Protected traffic.** From this point, all traffic is encrypted and authenticated. Anyone in the middle cannot read it or change it without being detected.

**Speed.** TLS 1.3 completes the handshake in one round trip. TLS 1.2 needs two, so TLS 1.3 connections start faster.

**What HTTPS does not prove.** The certificate tells you nothing about who runs the site. It proves only that whoever controls the domain also controls the matching key. A phishing site can have a valid certificate for its own domain. The padlock means your connection is private, not that the site is honest.
