I wouldn't do it. Keep integrity rules in the DB and business logic in the app, behind one entry point.

**The upside is real.** With triggers, no application path can skip the rule. Not even a script someone runs by hand.

**The cost is high:**
- **Hidden behavior.** Someone reading the app code can't see the triggers. A change that looks simple can fire others and leave no trace.
- **Testing.** Your team's current test tools don't cover triggers. You'd need tests that run against a real database.
- **Debugging.** An error inside a trigger shows up only as a failed write. It doesn't say which rule caused it.
- **Fragile migrations.** Trigger order matters, and nothing declares it.

**Better split:**
- **Database:** only what protects integrity: constraints, foreign keys, uniqueness and domain checks.
- **Application:** the business logic, behind a single entry point.

The single entry point gives the same guarantee as a trigger, provided only migrations get direct database access. That access rule is the real enforcement point. If anyone else can write to the DB directly, the business rules can be bypassed.
