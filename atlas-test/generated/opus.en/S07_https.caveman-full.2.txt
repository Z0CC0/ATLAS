HTTPS is HTTP running inside a channel that TLS encrypts. A TLS handshake sets up that channel before any HTTP data goes through.

**Handshake**

1. Client opens the connection and lists the TLS versions and ciphers it supports.
2. Server picks one cipher and one version, then sends its certificate.
3. Client checks the certificate. The certificate binds a domain name to a public key, and a certificate authority signs it. The client checks the signature by walking the chain up to a root certificate it already holds.
4. Client and server agree on a session key. Today this is typically an elliptic curve Diffie-Hellman exchange.

**Why a symmetric session key**

Asymmetric encryption costs too much for real traffic. The public key only helps set up trust. Bulk data then uses the cheaper symmetric session key.

**After handshake**

From here all traffic is encrypted and authenticated. Anyone in the middle can neither read it nor change it.

**Speed**

TLS 1.3 needs only one round trip for the handshake. TLS 1.2 needs two.

**Limit to know**

A valid certificate says nothing about who runs the site. It proves only that the domain controls that key. A padlock means "you talk privately to this domain". It does not mean "this domain is trustworthy".
