**I wouldn't put all of it there.** Keep integrity rules in the database and business logic in the application.

The upside is real: no application path can skip the rule, not even a script someone runs by hand.

The costs:

Triggers are invisible from the application code. A change that looks simple can fire other triggers without leaving a trace.

Your team's current test tools don't cover them. You'd need tests running against a real database.

Debugging gets harder. An error inside a trigger shows up only as a failed write and doesn't say which rule caused it.

Migrations get fragile. Trigger order matters, and nothing declares it.

The alternative: the database keeps constraints, foreign keys, uniqueness and domain checks. The business logic lives in the application, behind a single entry point. That gives the same guarantee as triggers, **as long as direct database access is reserved for migrations**.
