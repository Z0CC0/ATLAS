Don't run `ALTER TABLE ... ALTER COLUMN ... TYPE integer` directly. On a table this size it rewrites the whole table while holding an ACCESS EXCLUSIVE lock, so the service is down for as long as the rewrite takes. Instead, move the data to a new column in stages:

**1. Check that every value can be converted.** Count the rows where the value isn't all digits:

```sql
SELECT count(*) FROM t WHERE colonna !~ '^[0-9]+$';
```

If the count isn't zero, fix those rows before you go on.

**2. Add the new column:**

```sql
ALTER TABLE t ADD COLUMN colonna_int integer;
```

**3. Fill it in batches of 10,000 rows.** Small batches mean no long lock is held on the table, and the service keeps running while the data is copied.

**4. Add a trigger that keeps the two columns in step.** While the migration runs, any row that gets written to also updates `colonna_int`, so the new column doesn't fall behind.

**5. Change the code to read from `colonna_int`, and ship it.**

**6. Only then, drop the old column:**

```sql
ALTER TABLE t DROP COLUMN colonna;
```

This last step can't be undone. Once the column is dropped, the only way to get the data back is to restore from backup. Wait until the new column is filled and the code that reads from it is running in production before you drop the old one.
