Don't do it with a direct `ALTER TABLE ... ALTER COLUMN ... TYPE integer`. On ten million rows that rewrites the whole table while holding an `ACCESS EXCLUSIVE` lock, so your service is down for as long as the rewrite runs. Do the change in steps instead:

1. **Check that every value can be converted.** Count the rows in `colonna` that aren't all digits. If the count isn't zero, fix those rows before you go on, or they'll break the conversion partway through.

2. **Add the new column:**
   ```sql
   ALTER TABLE t ADD COLUMN colonna_int integer;
   ```

3. **Fill it in batches of 10,000 rows.** Converting and copying `colonna` into `colonna_int` a slice at a time means no single statement holds a long lock on the table, so normal traffic keeps flowing while you work.

4. **Add a trigger that keeps the two columns in step.** Rows inserted or updated during the migration then get `colonna_int` filled too, and the new column doesn't fall behind while you backfill.

5. **Change your code to read from `colonna_int`, and ship it.** Confirm that production is running on the new column.

6. **Only then, drop the old column:**
   ```sql
   ALTER TABLE t DROP COLUMN colonna;
   ```

Step 6 can't be undone. Once the column is dropped, the data comes back only if you restore from a backup. Everything before it can be rolled back, so don't rush this step: run it only after the new code has been running on `colonna_int` and you're sure nothing still reads `colonna`.
