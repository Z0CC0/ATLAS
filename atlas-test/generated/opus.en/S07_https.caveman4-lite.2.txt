HTTPS is ordinary HTTP sent through a channel that TLS encrypts. The TLS handshake sets up that channel before any HTTP data moves.

**Handshake:**

1. The client opens the connection. It lists the TLS versions and ciphers it supports.
2. The server picks one cipher and one version. It replies with that choice and its certificate.
3. The client checks the certificate. The certificate binds a domain name to a public key, and a certificate authority (CA) signs it. The client follows the chain of signatures up to a root certificate it already holds.
4. Client and server agree on a session key. Today this is usually done with an elliptic curve Diffie-Hellman exchange.

**After the handshake:** all traffic is encrypted and authenticated. Anyone in the middle can't read it or change it.

**Why the session key is symmetric:** asymmetric encryption costs too much to use on real traffic. Public keys only set up the connection. A fast symmetric key carries the data.

**TLS 1.3 vs 1.2:** in TLS 1.3 the handshake takes one round trip. In TLS 1.2 it takes two.

**What a certificate doesn't prove:** it says nothing about who runs the site. It only proves that whoever controls the domain also controls that key. A valid padlock on a phishing domain is still valid.
