I wouldn't put all of it in triggers. The upside is real: no application path can skip the rule, not even a script run by hand. The costs:

Nobody reading the application code can see triggers. A change that looks simple can set off others and leave no trace.

Your team's current test tools don't cover them. You need tests that run against a real database.

Debugging gets worse. An error inside a trigger shows up as a failed write and doesn't say which rule caused it.

Migrations get fragile. Trigger order matters, and nothing declares it.

**Alternative:** keep in the database only what protects integrity: constraints, foreign keys, uniqueness and domain checks. Put the business logic in the application, behind a single entry point.

That entry point gives you the same guarantee as a trigger, **as long as direct database access is reserved to migrations**.
