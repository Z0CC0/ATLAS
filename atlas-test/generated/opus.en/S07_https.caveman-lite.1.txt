HTTPS is ordinary HTTP carried inside a channel that TLS encrypts. The HTTP requests and responses stay the same. The difference is the protected channel around them, which TLS sets up with a handshake before any HTTP data moves.

**1. Hello from the client.** The client opens the connection. It lists the TLS versions and ciphers it supports.

**2. The server answers.** The server picks one version and one cipher from that list. It also sends its certificate.

**3. The client checks the certificate.** A certificate binds a domain name to a public key. A certificate authority (CA) signs it. To verify that signature, the client walks the chain of signatures up to a root certificate it already holds. If the chain does not end at a trusted root, the client rejects the certificate.

**4. Both sides agree on a session key.** Today this is usually an elliptic curve Diffie-Hellman (ECDHE) exchange. The session key is symmetric. Asymmetric encryption costs too much to use on real traffic, so it only helps set up the connection.

**5. Protected traffic.** From this point, the session key encrypts and authenticates all traffic. Anyone in the middle can neither read it nor modify it.

**Speed:** TLS 1.3 finishes the handshake in a single round trip. TLS 1.2 needs two, so with TLS 1.3 the connection is ready sooner.

**What the padlock does not tell you:** The certificate says nothing about who runs the site. It only says that whoever controls the domain also controls that key. A phishing site can have a valid certificate for its own domain. HTTPS proves you are talking privately to that domain, not that the domain is trustworthy.
