Don't do it with a single `ALTER TABLE ... ALTER COLUMN ... TYPE integer`. On a table this size, that statement rewrites the whole table while holding an `ACCESS EXCLUSIVE` lock, so your service is down for as long as the rewrite takes. Instead, add a new column next to the old one, move the data over gradually, and drop the old column at the very end.

**1. Check that every value can be converted**

Count the rows where the value isn't all digits:

```sql
SELECT count(*) FROM t WHERE colonna !~ '^[0-9]+$';
```

If the count isn't zero, fix or decide how to handle those rows before you go further.

**2. Add the new column**

```sql
ALTER TABLE t ADD COLUMN colonna_int integer;
```

**3. Copy the data in batches of 10,000 rows**

Run an update like this repeatedly until no rows are left to fill. Each batch is small, so no long lock is held on the table and normal traffic keeps flowing.

```sql
UPDATE t SET colonna_int = colonna::integer
WHERE id IN (
  SELECT id FROM t WHERE colonna_int IS NULL LIMIT 10000
);
```

**4. Add a trigger to keep the two columns in sync**

While the migration is running, the application keeps writing to `colonna`. A trigger copies each insert or update into `colonna_int`, so the new column doesn't fall behind the old one.

**5. Change the code to read from `colonna_int` and ship it**

Make sure that release is deployed and working before you continue.

**6. Only then, drop the old column**

```sql
ALTER TABLE t DROP COLUMN colonna;
```

Be careful with this step because it can't be undone. Once the column is dropped, the data only comes back if you restore from a backup. Don't run it until you're sure nothing reads `colonna` anymore.
