I wouldn't put all of it in triggers. Keep only integrity rules in the database, and put the business logic in the application behind a single entry point.

The upside is real. With triggers, no application path can skip a rule, not even a script someone runs by hand.

The costs are bigger, though.

Triggers can't be seen by anyone reading the application code. A change that looks simple can fire other triggers and leave no trace.

The team can't test them with the tools it already uses. You'd need tests that run against a real database.

Debugging gets worse. When a trigger fails, you only see a failed write. It doesn't say which rule caused it.

Migrations become fragile, because trigger order matters and nothing declares it.

The alternative:

1. Keep in the database only what protects integrity: constraints, foreign keys, uniqueness and domain checks.
2. Put the business logic in the application, behind a single entry point.

That entry point gives you the same guarantee a trigger would, **as long as direct database access is reserved for migrations only**. The "impossible to bypass" guarantee depends on that access rule.
