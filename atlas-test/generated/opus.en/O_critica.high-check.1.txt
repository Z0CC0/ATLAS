I wouldn't put all of it in triggers. Keep integrity rules in the database and business logic in the application, behind a single entry point.

The upside is real: no application path can skip the rule, not even a script someone runs by hand.

The costs:

Anyone reading the application code can't see triggers, so a change that looks simple can fire other triggers and leave no trace.

Your team's current test tools won't cover them. You'd need tests that run against a real database.

Debugging gets harder. An error inside a trigger shows up only as a failed write and doesn't say which rule caused it.

Migrations become fragile, because trigger order matters and nothing declares it.

The alternative is to keep in the database only what protects integrity: constraints, foreign keys, uniqueness and domain checks. The business logic goes in the application, behind one entry point.

That entry point gives you the same guarantee as a trigger, but only if direct database access is reserved for migrations.
