I wouldn't put all of it in triggers. Keep integrity rules in the database and business logic in the application, behind a single entry point.

You're right about the upside: with triggers, no application path can skip the rule, not even a script someone runs by hand.

The costs are high, though. Someone reading the application code can't see triggers, so a change that looks simple can fire others and leave no trace.

Your team's usual testing tools won't cover triggers. You'd need tests that run against a real database.

Debugging gets harder. An error inside a trigger shows up only as a failed write, with no sign of which rule caused it.

Migrations become fragile. Trigger order matters, and nothing declares it.

A better split:

In the database: only what protects integrity. That means constraints, foreign keys, uniqueness and domain checks.

In the application: the business logic, with every write going through a single entry point.

That entry point gives you the same guarantee a trigger would, **as long as only migrations have direct access to the database**.
