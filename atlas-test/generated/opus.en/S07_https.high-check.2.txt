internal knowledge

HTTPS is HTTP running inside a channel encrypted by TLS.

The handshake:

1. The client opens the connection and says which TLS versions and ciphers it supports.

2. The server picks a cipher and a version, and sends its certificate.

3. The client checks the certificate's signature by following the chain up to a root certificate it already holds.

4. Client and server agree on a session key. Today this is typically done with an elliptic curve Diffie-Hellman exchange.

The certificate binds a domain name to a public key, and a certificate authority signs it. It says nothing about who runs the site. It only says that the domain controls that key.

The session key is symmetric because asymmetric encryption costs too much for real traffic.

After the handshake, all traffic is encrypted and authenticated. Anyone in the middle can neither read it nor change it.

TLS 1.3 finishes the handshake in one round trip. TLS 1.2 needs two.
