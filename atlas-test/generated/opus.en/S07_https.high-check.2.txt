internal knowledge

HTTPS is HTTP sent through a channel that TLS encrypts.

1. The client opens the connection and lists the TLS versions and ciphers it supports.
2. The server picks a version and a cipher, and sends its certificate.
3. The client checks the certificate's signature by following the chain up to a root certificate it already has.
4. Client and server agree on a session key, these days usually through an elliptic curve Diffie-Hellman exchange.
5. From then on, all traffic is encrypted and authenticated. Anyone in the middle can neither read it nor change it.

The certificate links a domain name to a public key, and a certificate authority signs it. It does not tell you who runs the site. It only shows that the domain controls that key.

The session key is symmetric because asymmetric encryption is too slow for real traffic.

In TLS 1.3 the handshake takes a single round trip. TLS 1.2 needs two.
