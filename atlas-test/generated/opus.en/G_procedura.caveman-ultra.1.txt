Don't use a direct `ALTER TABLE ... ALTER COLUMN ... TYPE integer`. That command rewrites the whole table while holding an ACCESS EXCLUSIVE lock. Your service stays down until the rewrite finishes, and on ten million rows that takes a while.

Do the change in six steps instead, in this order:

1. **Check that every value converts.** Count the rows whose value is not all digits. If the count is not zero, fix those rows before you start.

2. **Add the new column.**
   ```sql
   ALTER TABLE t ADD COLUMN colonna_int integer;
   ```

3. **Fill the new column in batches of 10,000 rows.** Small batches mean no long lock is held on the table, so the service keeps running.

4. **Add a trigger that keeps both columns in step.** Rows written during the migration then reach `colonna_int` too.

5. **Change the code to read from `colonna_int`, and ship it.**

6. **Only after that, drop the old column.**

> **Warning:** Step 6 cannot be undone. After you drop the column, the only way to get its data back is a restore from backup. Run it only when the new code is live and working on `colonna_int`.
> ```sql
> ALTER TABLE t DROP COLUMN colonna;
> ```
