Don't run `ALTER TABLE t ALTER COLUMN colonna TYPE integer` directly. It rewrites all ten million rows while holding an ACCESS EXCLUSIVE lock, so your service is down for as long as the rewrite takes. Move the data to a new column instead:

1. **Check every value converts.** Count the rows where `colonna` is not all digits. If the count isn't 0, fix those rows before you go on.
2. **Add the new column:**
   ```sql
   ALTER TABLE t ADD COLUMN colonna_int integer;
   ```
3. **Fill it in batches of 10,000 rows.** Small batches mean no long lock is held on the table, so the service keeps running.
4. **Add a trigger that keeps `colonna` and `colonna_int` matching** while the migration runs. Rows written during the backfill stay correct.
5. **Change the code to read from `colonna_int`, and ship it.**
6. **Only after that, drop the old column:**
   ```sql
   ALTER TABLE t DROP COLUMN colonna;
   ```

⚠️ Step 6 can't be undone. Once the column is dropped, the only way to get that data back is a restore from backup. Run it only after the code from step 5 is live and reading from `colonna_int`.
