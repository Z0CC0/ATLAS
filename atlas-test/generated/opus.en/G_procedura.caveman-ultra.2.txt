Don't run `ALTER TABLE t ALTER COLUMN colonna TYPE integer` directly. That command rewrites the whole table and holds an `ACCESS EXCLUSIVE` lock the entire time. On ten million rows, your service is down for as long as the rewrite takes.

Do the change in six steps, in this order:

1. **Check the data.** Count the rows where `colonna` is not all digits. If the count is not zero, fix or handle those rows before you go on. Otherwise the conversion fails partway through.

2. **Add the new column.**
   ```sql
   ALTER TABLE t ADD COLUMN colonna_int integer;
   ```

3. **Fill `colonna_int` in batches of 10,000 rows.** Small batches never hold a long lock on the table, so the service keeps running.

4. **Add a trigger that keeps both columns in sync.** Rows written during the migration also get the correct `colonna_int` value, so nothing is missed between batches.

5. **Change the code to read from `colonna_int`, and ship it.** Confirm it works in production before you continue.

6. **Only after that, drop the old column.**

> **Warning:** This step cannot be undone. Once `colonna` is dropped, the only way to get its data back is to restore from backup.
> ```sql
> ALTER TABLE t DROP COLUMN colonna;
> ```

Steps 1 to 5 can all be rolled back, because the old column still exists. Step 6 is the only one with no way back, so it goes last, after the new code is proven in production.
