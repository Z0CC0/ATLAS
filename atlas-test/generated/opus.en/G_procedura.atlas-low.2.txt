Don't change the type in place. Add a new column, move the data over, and remove the old column last.

A direct `ALTER TABLE ... ALTER COLUMN ... TYPE` rewrites the whole table while holding an ACCESS EXCLUSIVE lock. On ten million rows, that means the service is down for as long as the rewrite takes.

Do these steps in this order:

1. Check that every existing value can be converted. Count the rows whose value is not all digits. If the count is not zero, fix those rows before you go on.
2. Add the new column:
   ```sql
   ALTER TABLE t ADD COLUMN colonna_int integer;
   ```
3. Fill the new column in batches of ten thousand rows. Small batches mean no long lock is held on the table.
4. Add a trigger that keeps the two columns in step for as long as the migration runs.
5. Change the code to read from `colonna_int`, and ship it.
6. Only after all of that, drop the old column:
   ```sql
   ALTER TABLE t DROP COLUMN colonna;
   ```

Step 6 cannot be undone. Once the column is dropped, the data only comes back if you restore from a backup. Don't drop it until the code running from the new column has been confirmed to work.
