Wrap the connection acquire and release in `db/session.py:47` in `try/finally`:

```python
conn = pool.acquire()
try:
    return handler(conn, request)
finally:
    pool.release(conn)
```

## What's happening

The cause is connection pool exhaustion. It is not a slow query.

- The middleware at `db/session.py:47` releases the connection only when the handler succeeds.
- When the handler raises an exception, `release()` never runs. The connection stays held until it times out.
- After a few hundred failed requests the pool is empty, and every request after that waits for a connection.
- Requests wait instead of failing, so you see latency climbing until the API locks up, not immediate errors.

The `finally` block runs on the error path too, so connections from failed requests go back to the pool.

## Don't raise `pool_size` first

Raising `pool_size` looks like a fix, but it only hides the leak. A bigger pool takes longer to empty, so the lockup comes later, but connections still leak. Raise it only after the fix is in, and only if your real load needs it.

2. Apply the `try/finally` change at `db/session.py:47`.
