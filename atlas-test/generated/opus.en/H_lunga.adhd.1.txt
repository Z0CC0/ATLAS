## Prompt caching in short

Put everything that stays the same at the start of the prompt and everything that changes at the end. Caching saves money only when many requests begin with the same text.

## How it works

- The cache stores the start of a request (the prefix) after the model has processed it.
- When a later request begins with the same text, that part is not paid for again.
- Only a shared prefix can be reused. If even one character differs early on, nothing from that character onward is reused.

## How to order your prompt

1. **Stable parts first:** system instructions, attached documentation, tool definitions
2. **Changing parts last:** the user's new message, the latest turn

If you reverse that order, the changing part comes first and breaks reuse of everything after it.

**A common mistake:** a system line that changes every turn, such as a clock or timestamp, stops reuse of everything after it. The large stable context that follows it gets processed and paid for again on every request.

## Cost over time

- **Request 1 costs more.** Writing to the cache is more expensive than a normal read.
- **Savings start at request 2.** From then on, the cached prefix is read back instead of processed again.
- **Savings grow with each turn.** The more turns reuse the same prefix, the more the first-request cost is covered.

## When it pays off

| Pays off | Doesn't pay off |
|---|---|
| Long conversations | Single, one-off requests |
| Large stable context (instructions, docs, tools) | Requests that each differ from one another |
| Many turns sharing the same prefix | You pay for the cache write and never read it back |

Next: open your system prompt and look for anything that changes per request, such as a date, time, or request ID. If you find one, move it to the end.
