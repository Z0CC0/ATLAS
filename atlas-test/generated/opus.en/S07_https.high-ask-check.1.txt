internal knowledge

HTTPS is HTTP running inside a channel that TLS encrypts.

Handshake:

1. Client opens the connection and lists the TLS versions and ciphers it supports.

2. Server picks a version and a cipher, and sends its certificate.

3. Client checks the certificate's signature by following the chain up to a root certificate it already holds.

4. Client and server agree on a session key, today usually through an elliptic curve Diffie-Hellman exchange.

The certificate links a domain name to a public key, and a certificate authority signs it. It does **not** say who runs the site. It only shows that whoever controls the domain controls that key.

The session key is symmetric because asymmetric encryption costs too much for real traffic.

After the handshake, traffic is encrypted and authenticated. Anyone in the middle can neither read it nor change it.

TLS 1.3 completes the handshake in one round trip. TLS 1.2 needs two.
