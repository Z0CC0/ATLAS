internal knowledge

HTTPS means HTTP running inside a channel that TLS encrypts. Before any page data moves, client and server run a handshake to set that channel up:

1. Client opens the connection and lists the TLS versions and ciphers it supports.

2. Server picks one version and one cipher, and sends back its certificate.

3. Client checks the certificate. The certificate binds a domain name to a public key, and a certificate authority signs it. Client verifies that signature by following the chain up to a root certificate it already holds.

4. Client and server agree on a session key. Today they usually do this with an elliptic curve Diffie-Hellman exchange.

The session key is symmetric because asymmetric encryption costs too much for real traffic. Asymmetric cryptography only helps set up the connection. The bulk of the data uses the cheaper symmetric key.

After the handshake, traffic is encrypted and authenticated. Anyone in the middle can neither read it nor change it without detection.

TLS 1.3 needs a single round trip for the handshake. TLS 1.2 needs two, so connections under 1.3 start faster.

One common misunderstanding: the padlock does **not** tell you who runs the site. The certificate proves only that whoever controls the domain also controls that key. A phishing site on its own domain can have a perfectly valid certificate.
