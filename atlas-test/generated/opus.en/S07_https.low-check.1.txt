internal knowledge

HTTPS is ordinary HTTP running inside a channel encrypted by TLS. Before any HTTP request goes out, client and server do a TLS handshake:

1. Client opens the connection and lists which TLS versions and ciphers it supports.

2. Server picks one cipher and one version, and sends its certificate.

3. Client checks the certificate. A certificate binds a domain name to a public key and is signed by a certificate authority. Client verifies that signature by following the chain of signers up to a root certificate it already holds.

4. Client and server agree on a session key. Today this is typically done with an elliptic curve Diffie-Hellman exchange.

The session key is symmetric because asymmetric encryption costs too much to use on real traffic. Asymmetric cryptography only sets up the connection, and the symmetric key protects the data.

From that point on, traffic is encrypted and authenticated. Anyone in the middle can neither read it nor modify it.

TLS 1.3 completes the handshake in a single round trip. TLS 1.2 needs two.

**The certificate says nothing about who runs the site.** It proves only that whoever controls that domain also controls that key.
