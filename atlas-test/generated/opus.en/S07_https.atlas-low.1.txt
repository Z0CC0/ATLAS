HTTPS is ordinary HTTP sent through a channel that TLS encrypts. Before any HTTP data moves, client and server run a handshake to set up that channel:

1. The client opens the connection and lists the TLS versions and ciphers it supports.

2. The server picks a version and a cipher and sends back its certificate. The certificate binds a domain name to a public key, and a certificate authority signs it.

3. The client checks that signature by walking the chain of certificates up to a root certificate it already holds.

4. Client and server agree on a session key. Today this is usually done with an elliptic curve Diffie-Hellman exchange.

The session key is symmetric because asymmetric encryption costs too much to use on real traffic. From that point on, all traffic is encrypted and authenticated, so nobody in the middle can read it or change it.

In TLS 1.3 the handshake takes one round trip. TLS 1.2 needed two.

**The certificate says nothing about who runs the site.** It only shows that whoever controls the domain also controls that key.
