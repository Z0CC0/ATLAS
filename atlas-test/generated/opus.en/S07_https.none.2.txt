HTTPS is ordinary HTTP carried inside a channel that TLS encrypts. The web traffic itself stays the same, but everything travels through a protected tunnel. Most of the work happens in a short negotiation at the start of the connection, called the handshake.

**The handshake**

1. **The client says hello.** Your browser opens the connection and lists the TLS versions and ciphers it supports.
2. **The server replies.** It picks one cipher and one version from that list and sends back its certificate.
3. **The client checks the certificate.** A certificate binds a domain name to a public key, and a certificate authority signs it. To check that signature, the browser follows the chain of signatures upward until it reaches a root certificate it already holds. If the chain ends at a root it trusts, the certificate is accepted.
4. **Both sides agree on a session key.** Today this is usually done with an elliptic curve Diffie-Hellman exchange. The session key is symmetric, meaning the same key encrypts and decrypts. Asymmetric encryption is used only during setup because it is too expensive to run on real traffic.

**After the handshake**

From here on, all traffic is encrypted and authenticated. Someone sitting between you and the server can't read it, and can't change it without being detected.

**Speed: TLS 1.2 vs 1.3**

The handshake adds delay before any page data can flow. TLS 1.2 needs two round trips between client and server. TLS 1.3 needs only one, which is a big part of why it is faster.

**What the padlock doesn't tell you**

A valid certificate says nothing about who runs the site. It proves only that whoever controls the domain also controls that key. A phishing site on a lookalike domain can have a perfectly valid certificate, so HTTPS protects the connection but doesn't make the site trustworthy.
