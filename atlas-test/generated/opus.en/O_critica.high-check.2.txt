I wouldn't put everything in triggers. Keep only integrity rules in the database.

The upside is real: no application path can skip the rule, not even a script someone runs by hand.

The costs:

Nobody reading the application code can see triggers. A change that looks simple can fire other triggers and leave no trace.

Your team's usual test tools don't cover them. You need tests that run against a real database.

Debugging gets harder. An error inside a trigger shows up as a failed write and doesn't say which rule caused it.

Migrations become fragile. Trigger order matters, and nothing declares it.

**Alternative:** keep integrity rules in the database: constraints, foreign keys, uniqueness and domain checks. Put the business logic in the application, behind a single entry point.

That entry point gives you the same guarantee as a trigger, **as long as direct database access is reserved for migrations**.
