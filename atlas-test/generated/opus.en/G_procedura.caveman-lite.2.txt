Don't use `ALTER TABLE ... ALTER COLUMN ... TYPE integer` directly. It rewrites the whole table while holding an `ACCESS EXCLUSIVE` lock. With ten million rows, your service is down for the whole rewrite. Do the change in stages instead:

1. **Check that every value converts.** Count the rows where `colonna` is not all digits. If the count is not zero, fix those rows before you go on.

2. **Add the new column:**
   ```sql
   ALTER TABLE t ADD COLUMN colonna_int integer;
   ```

3. **Backfill `colonna_int` in batches of 10,000 rows.** Small batches mean no long lock is held on the table, so normal traffic keeps running.

4. **Add a trigger that keeps `colonna` and `colonna_int` in step.** Rows written or updated during the migration then stay consistent in both columns.

5. **Change your code to read from `colonna_int` and ship it.**

6. **Only after step 5 is live, drop the old column:**
   ```sql
   ALTER TABLE t DROP COLUMN colonna;
   ```

**Warning:** Step 6 can't be undone. Once you drop `colonna`, the only way to get its data back is to restore from backup. Before you run it, make sure the new code is in production and reading from `colonna_int`.
