internal knowledge

HTTPS is plain HTTP carried inside a channel that TLS encrypts. Before any HTTP is sent, client and server run a TLS handshake:

1. Client opens the connection and states which TLS versions and ciphers it supports.

2. Server answers by picking one cipher and one version, and sends its certificate.

3. Client checks the certificate. It binds a domain name to a public key and is signed by a certificate authority. Client verifies that signature by following the chain up to a root it already holds.

4. Both sides agree on a session key, today typically with an elliptic curve Diffie-Hellman exchange.

After that, traffic is encrypted and authenticated. Anyone in the middle can neither read it nor change it.

Session key is symmetric because asymmetric encryption costs too much for real traffic.

TLS 1.3 completes the handshake in a single round trip. TLS 1.2 needs two.

One limit: **the certificate says nothing about who runs the site.** It says only that the domain controls that key.
