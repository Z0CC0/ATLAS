I wouldn't put all of it there. Keep only integrity rules in the database and put the business logic behind a single entry point in the application.

The upside you're after is real. With triggers, no application path can skip a rule, not even a script someone runs by hand.

The costs are high, though:

Nobody reading the application code can see triggers. A change that looks simple can fire other triggers and leave no trace.

Your team's current testing tools won't cover them. Every rule needs tests that run against a real database.

Debugging gets worse. When a trigger fails, you just get a failed write, with nothing saying which rule caused it.

Migrations get fragile. Trigger order matters, but nothing declares it.

The alternative: keep in the database only what protects data integrity, meaning constraints, foreign keys, uniqueness and domain checks. Put the business logic in the application, behind one entry point that every write goes through.

That entry point gives you the same guarantee as triggers **as long as only migrations get direct access to the database**. Enforce that restriction and nothing can bypass the rules, and you avoid the problems above.
