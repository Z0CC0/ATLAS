HTTPS means ordinary HTTP carried inside a channel that TLS encrypts. Before any HTTP flows, client and server run a TLS handshake:

1. The client opens the connection and lists the TLS versions and ciphers it supports.
2. The server picks a version and a cipher, and sends its certificate.
3. The client checks the certificate. A certificate binds a domain name to a public key and is signed by a certificate authority. The client verifies that signature by following the chain up to a root certificate it already holds.
4. Client and server agree on a session key. Today this is typically done with an elliptic curve Diffie-Hellman exchange.

From then on, all traffic is encrypted and authenticated. Anyone in the middle can neither read it nor change it.

The session key is symmetric because asymmetric encryption costs too much to use on real traffic. The asymmetric part only sets up the connection.

TLS 1.3 completes the handshake in a single round trip. TLS 1.2 needs two.

A valid certificate does **not** tell you who runs the site. It only proves that whoever is answering for that domain controls that key.
