I wouldn't put all of it in triggers. Put integrity in the DB and business logic in the app.

**Upside is real.** With triggers, no application path can skip the rule, not even a script run by hand.

**Costs:**
- **Hidden behavior.** Triggers don't show up in application code. A change that looks simple can fire other triggers and leave no trace.
- **Testing.** The team's current test tools don't cover triggers. You need tests that run against a real database.
- **Debugging.** An error inside a trigger arrives as a failed write. It doesn't say which rule caused it.
- **Migrations.** They get fragile. Trigger order matters, and nothing declares it.

**Recommendation:**
- **In the DB, only what protects integrity:** constraints, foreign keys, uniqueness and domain checks.
- **In the application, the business logic,** behind one single entry point.
- **Only migrations get direct DB access.** Under that rule, the single entry point gives the same guarantee as a trigger: nothing can bypass it.

The hard part is enforcing that access rule. If anyone or anything can still write to the DB directly, the guarantee is gone.
