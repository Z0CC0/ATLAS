Start by counting the rows that won't convert. Run this, and don't continue until it returns 0:

```sql
SELECT count(*) FROM t WHERE colonna !~ '^[0-9]+$';
```

**Don't use `ALTER TABLE t ALTER COLUMN colonna TYPE integer`.** It rewrites the whole table while holding an ACCESS EXCLUSIVE lock, so the service is down for as long as that takes. On ten million rows, that means downtime.

Do the change in stages instead:

1. **Check the data.** Run the count query above. If any value isn't all digits, fix those rows first.
2. **Add the new column:**
   ```sql
   ALTER TABLE t ADD COLUMN colonna_int integer;
   ```
3. **Fill it in batches of 10,000 rows.** Each batch is short, so no long lock is held on the table and the service stays up.
4. **Add a trigger that keeps `colonna` and `colonna_int` in step.** New writes during the migration then land in both columns.
5. **Change the code to read from `colonna_int`, and ship it.**
6. **Only after step 5 is live, drop the old column:**
   ```sql
   ALTER TABLE t DROP COLUMN colonna;
   ```

⚠️ **Step 6 can't be undone.** Once you drop the column, the data comes back only by restoring from a backup. Don't run it until the new code is in production and reading from `colonna_int`.
