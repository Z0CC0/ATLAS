internal knowledge

Don't run `ALTER TABLE ... ALTER COLUMN ... TYPE integer` directly. It rewrites the whole table while holding an ACCESS EXCLUSIVE lock, so the service is down for the entire rewrite. Do the change in these steps instead, in this order:

1. Check that every existing value can be converted. Count the rows that are not all digits, for example:
   ```sql
   SELECT count(*) FROM t WHERE colonna !~ '^[0-9]+$';
   ```
   If the count isn't zero, fix those rows before going on.

2. Add the new column:
   ```sql
   ALTER TABLE t ADD COLUMN colonna_int integer;
   ```

3. Fill `colonna_int` in batches of 10,000 rows, so no long lock is held on the table.

4. Add a trigger that keeps `colonna` and `colonna_int` in step while the migration runs, so rows written during the backfill stay consistent.

5. Change the application code to read from `colonna_int`, and ship it.

6. Only after that, drop the old column:
   ```sql
   ALTER TABLE t DROP COLUMN colonna;
   ```

**Step 6 can't be undone.** Once the column is dropped, its data only comes back by restoring from backup. Don't run it until the code reading `colonna_int` has shipped.
