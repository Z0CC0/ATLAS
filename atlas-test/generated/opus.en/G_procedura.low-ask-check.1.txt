internal knowledge

Don't change the type in place. Add a new integer column next to the old one, move the data over gradually, and drop the old column only at the end.

A direct `ALTER TABLE ALTER COLUMN TYPE` rewrites the whole table while holding an ACCESS EXCLUSIVE lock. On ten million rows, that means the service is down for as long as the rewrite takes.

Do it in this order:

1. Check that every existing value can be converted. Count the rows where the value is not all digits. If that count isn't zero, deal with those rows before going further.

2. Add the new column:
```sql
ALTER TABLE t ADD COLUMN colonna_int integer;
```

3. Fill it in batches of ten thousand rows, so no long lock is held on the table.

4. Add a trigger that keeps the two columns in step while the migration runs. That way, writes that happen during and after the backfill also reach `colonna_int`.

5. Change the code to read from the new column, and ship it.

6. Only then, drop the old column:
```sql
ALTER TABLE t DROP COLUMN colonna;
```

**Step 6 can't be undone.** Once the column is dropped, the data comes back only with a restore from backup. Don't run it until the code reading `colonna_int` is live and working.
