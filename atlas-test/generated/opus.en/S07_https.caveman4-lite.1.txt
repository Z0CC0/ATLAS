HTTPS is HTTP running inside a channel that TLS encrypts.

**Handshake**
1. Client opens the connection. It lists the TLS versions and ciphers it supports.
2. Server replies with its chosen cipher and version, plus its certificate.
3. The certificate binds a domain name to a public key. A certificate authority (CA) signs it.
4. Client checks the signature by walking the chain up to a root certificate it already holds.
5. Client and server agree on a session key. Today this is usually an elliptic curve Diffie-Hellman (ECDHE) exchange.

**Why a symmetric key:** asymmetric encryption costs too much for real traffic. It is used only to set up the session. The bulk data then uses the cheap symmetric session key.

**After the handshake:** all traffic is encrypted and authenticated. Anyone in the middle can neither read it nor change it.

**Speed:** TLS 1.3 completes the handshake in one round trip. TLS 1.2 needs two.

**Limit:** the certificate says nothing about who runs the site. It proves only that the domain controls that key. A valid padlock on a scam domain is still a scam.
