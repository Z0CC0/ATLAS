Your connection pool is running out of connections. It's a leak, not a slow query.

## What's happening

In the middleware at `db/session.py:47`, the connection only gets released when the request succeeds. If the handler raises an exception, the code never reaches `release()`, so that connection stays checked out until it times out.

Each failed request holds on to one connection. After a few hundred failures the pool is empty, and every request after that has to wait for a connection to free up. That's why latency keeps climbing and then the API locks up, rather than returning errors right away: requests are stuck waiting for connections the failed requests never gave back.

## The fix

Wrap the acquisition in `try/finally` so the connection is released on the error path too:

```python
conn = pool.acquire()
try:
    return handler(conn, request)
finally:
    pool.release(conn)
```

## Don't just raise `pool_size`

Raising `pool_size` will look like it fixed things, but it only hides the problem. The leak is still there, so the pool still empties; it just takes longer. Put the `try/finally` fix in first. After that, only raise `pool_size` if your real load needs more connections.

## Checking it

Run this before and after the change. Before, it should show the exhaustion; after, it shouldn't:

```
pytest tests/test_pool.py -k exhaustion -x
```
