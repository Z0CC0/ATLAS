I wouldn't put all of it there. Keep only integrity rules in the database, and put business logic in the application behind a single entry point.

The upside you're after is real. With triggers, no application path can skip the rule, not even a script someone runs by hand.

The cost comes later:

Triggers are invisible to anyone reading the application code. A change that looks simple can fire other triggers and leave no trace.

Your team's current test tools won't cover them. You'd need tests that run against a real database.

Debugging gets harder. An error inside a trigger shows up only as a failed write, with nothing saying which rule caused it.

Migrations become fragile, because the order triggers fire in matters and isn't declared anywhere.

A better split:

The database keeps what protects integrity: constraints, foreign keys, uniqueness and domain checks.

The application holds the business logic, and every write goes through one entry point.

That entry point gives you the same guarantee as a trigger, as long as direct database access is reserved for migrations. Without that rule, a hand-run script can go around it, and you're back to the problem you started with.
