I wouldn't put all of it in triggers. Keep only integrity rules in the database and put the business logic behind a single entry point in the application.

The upside is real: no application path can skip the rule, not even a script run by hand.

The costs:

Triggers are invisible to anyone reading application code. A change that looks simple can fire other changes and leave no trace.

You can't test them with the tools your team already uses. Tests have to run against a real database.

Debugging gets worse. An error inside a trigger arrives as a failed write and doesn't say which rule caused it.

Migrations become fragile, because trigger order matters and nothing declares it.

The alternative:

The database keeps only what protects integrity: constraints, foreign keys, uniqueness and domain checks.

The business logic lives in the application, behind a single entry point.

That entry point gives the same guarantee as a trigger, **but only if direct database access is reserved for migrations.**
