Prompt caching keeps the already-processed prefix of a request in memory, so requests that start the same way don't have to pay to reprocess that part again. But it's strictly prefix-based: if even one character near the start differs, everything from that point on is no longer reusable — the cache breaks there and there's no partial credit. That's why the order of your prompt matters: put the stable material first (system instructions, attached docs, tool definitions) and the parts that change turn to turn last. If you do it the other way round, a bit of shifting text at the top invalidates the reuse of everything stable that follows it.

There's a cost asymmetry too. The first time a prefix is cached, writing it costs more than a normal read — so the very first request in a sequence is actually more expensive than without caching. The payoff only shows up from the second request onward, and it compounds the more turns you have on top of that same stable prefix.

Put together, this means caching is a clear win for long conversations built on a large, unchanging context — a big system prompt, reference documentation, a stable set of tool definitions — where many turns get to reuse that same foundation. It does not pay off for one-off requests that each differ from one another: you'd pay the more expensive write every time and never get to the reads that make it worthwhile. And watch for anything in the stable prefix that quietly changes every turn — a timestamp or clock printed into the system message, for instance — since that alone will invalidate the cache for everything positioned after it, even if the rest of the prompt never changes.
