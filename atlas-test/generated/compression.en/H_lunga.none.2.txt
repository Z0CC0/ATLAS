Prompt caching lets you skip re-processing the part of a request you've already sent before. When a request comes in, the cache stores the prefix that's already been processed, so if a later request starts with that exact same content, that portion doesn't get paid for again.

The catch is it only works on the prefix. If even one character at the start differs, there's no reuse from that point onward — everything after the divergence is processed fresh. That's why the order of your content matters: put the stable stuff (system instructions, attached docs, tool definitions) first, and put the parts that change from turn to turn afterward. If you do it the other way around — changing content up front — you invalidate the cache for everything that follows, including the stable parts. A related trap: a system line that changes every turn, like a live clock or timestamp, kills the reuse of everything after it even if the rest is identical.

There's also a cost asymmetry to account for: writing to the cache costs more than a normal read. So the first request that populates the cache is actually more expensive than a normal uncached request. You only start gaining from the second request onward, and the benefit compounds — the more turns you run against that same stable prefix, the more you save overall.

That makes it a good fit for long conversations built on a large, stable context — think a chat session with a hefty system prompt, reference documentation, or a big set of tool definitions that doesn't change turn to turn. It's a poor fit for one-off, independent requests that differ from each other: in that case you pay the more expensive write and never get a read back to recoup it, so you just come out behind.
