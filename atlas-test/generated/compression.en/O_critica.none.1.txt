The instinct makes sense, and the upside is real: put the rule in a trigger and no application path can skip it — not even a script someone runs by hand straight against the database.

But that safety comes with costs that tend to surface later rather than up front. Triggers are invisible to anyone reading the application code — someone makes what looks like a simple change, and it silently fires other triggers with no trace in the code they're actually looking at. They also aren't tested with the tools your team already uses; to exercise them you need tests running against a real database. When something breaks, debugging is worse too: an error inside a trigger arrives as a failed write, without telling you which rule caused it. And migrations get fragile, because trigger execution order matters and is declared nowhere — so reordering or adding one can silently change behavior of others.

I'd keep the database doing only what protects integrity — constraints, foreign keys, uniqueness, domain checks — and put the business logic in the application, behind a single entry point. That entry point gives you the exact same "impossible to bypass" guarantee the trigger would, as long as direct database access is reserved for migrations only. You keep the safety without giving up visibility, testability, or sane debugging.
