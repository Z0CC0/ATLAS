I wouldn't put all of it in triggers. Put integrity rules in the database and business logic in the application, behind one entry point.

Upside real: no application path can skip rule, not even script run by hand.

Triggers invisible to anyone reading application code. Change that looks simple fires others with no trace.

Team's existing test tools don't cover them. You need tests running against real database.

Debugging gets worse. Error inside trigger arrives as failed write, without saying which rule caused it.

Migrations become fragile, because trigger order matters and is declared nowhere.

Instead, keep in database only what protects integrity: constraints, foreign keys, uniqueness, domain checks. Business logic lives in application, behind **single entry point**.

That entry point gives same guarantee as trigger, as long as **direct database access is reserved to migrations**.
