Don't put all logic in triggers.

Real upside: no path bypasses rule, not even script run by hand. But cost outweighs it.

Triggers invisible to anyone reading app code — simple change fires others with no trace. Not tested with tools team already uses; need tests against real database. Debugging worse: error inside trigger arrives as failed write, without saying which rule caused it. Migrations fragile too — trigger order matters, declared nowhere.

Keep in database only what protects integrity: constraints, foreign keys, uniqueness, domain checks. Business logic goes in application, behind single entry point. That entry point gives same guarantee as trigger — as long as direct database access stays reserved to migrations.
