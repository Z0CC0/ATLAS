Usually no. Postgres normally won't use a B-tree index on a low-cardinality column. When the filter matches more than roughly 5–10% of rows, the planner picks a sequential scan instead. The index still costs you on every write and takes disk space.

The exception is when one of the three values is rare. A partial index on just that value does get used:

```sql
CREATE INDEX ON orders (status) WHERE status = 'failed';
```
