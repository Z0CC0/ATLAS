I get the appeal — "no one can bypass it" is a strong guarantee. But I'd steer you away from putting business logic in triggers.

Here's the tradeoff: yes, a trigger can't be skipped, even by a script run by hand against the database. That part is real. Everything else about triggers works against you though. They're invisible to anyone reading the application code — someone changes what looks like a simple update, and it silently fires other logic elsewhere with no trace in the code they're looking at. You can't test them with the tools your team already uses; you'd need tests running against a real database instead of your normal test suite. Debugging gets worse, not better: when a trigger's rule fails, what you see is just a failed write, with nothing telling you which rule caused it. And migrations become fragile, because trigger execution order matters and it's declared nowhere — you're relying on people remembering it.

What gets you the same guarantee without those costs: keep the database responsible only for integrity — constraints, foreign keys, uniqueness, domain checks — and put the business logic in the application, behind a single entry point. That entry point gives you the identical "impossible to bypass" property, as long as direct database access is reserved for migrations and nothing else talks to the database directly. You get the guarantee you're after, but the logic stays visible, testable with your normal tools, and debuggable with a normal stack trace.
