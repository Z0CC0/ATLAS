I wouldn't do it. Keep only integrity rules in the database.

The upside is real: no application path can skip the rule, not even a script run by hand.

Triggers can't be seen from the application code, so a change that looks simple can fire others and leave no trace.

Your team's current test tools don't cover triggers. You need tests that run against a real database.

Debugging gets worse: an error inside a trigger shows up as a failed write and doesn't say which rule caused it.

Migrations become fragile, because trigger order matters and nothing declares it.

Instead, keep integrity in the database: constraints, foreign keys, uniqueness and domain checks. Put the business logic in the application, behind a single entry point.

That entry point gives the same guarantee as a trigger, as long as direct database access is reserved for migrations.
