That said, here's what's going on and how to fix it:

**What's happening**

This isn't a slow query — it's connection pool exhaustion. In your middleware, `db/session.py:47` only releases the connection on the success path. When a handler raises an exception, `release()` never runs, so that connection stays checked out until it eventually times out. Each failed request permanently (until timeout) eats one connection from the pool. After a few hundred of them, the pool is empty and every new request has to wait for one to free up — which is why you see latency climbing rather than an outright error the moment things go wrong. It looks like "the API is slow under load," but really it's "the API is quietly leaking connections every time a request errors."

**The fix**

Wrap the acquire/handle in a try/finally so release happens whether or not the handler raises:

```python
conn = pool.acquire()
try:
    return handler(conn, request)
finally:
    pool.release(conn)
```

That's the actual fix. Don't just bump `pool_size` — that only buys you more time before the pool empties again, it doesn't stop the leak. Raise `pool_size` afterward, and only if your real traffic actually needs a bigger pool.
