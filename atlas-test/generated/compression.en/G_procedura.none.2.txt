Migrating a `varchar` column to `integer` on a 10-million-row table in production isn't something you do with a single `ALTER TABLE ... ALTER COLUMN TYPE` — that statement rewrites the entire table and holds an ACCESS EXCLUSIVE lock the whole time, which means your service is down for as long as the rewrite takes. On a table that size, that's not acceptable.

Here's the safe path instead:

1. **Check the data is actually convertible.** Count how many existing rows are *not* all-digits — anything that isn't a clean integer string will break the conversion, so you need to know that number before doing anything else.

2. **Add the new column** alongside the old one:
   ```sql
   ALTER TABLE t ADD COLUMN colonna_int integer;
   ```

3. **Backfill in batches of 10,000 rows.** Never update all 10 million rows in one statement — that would hold a long lock too. Batching keeps each transaction short so the table stays available throughout.

4. **Add a trigger** that keeps `colonna` and `colonna_int` in sync for any writes that happen *during* the migration — otherwise rows written between your batches will drift out of sync.

5. **Switch your application code to read from `colonna_int`** and ship that change.

6. **Only after that's live and stable, drop the old column:**
   ```sql
   ALTER TABLE t DROP COLUMN colonna;
   ```

Be careful with that last step — it's irreversible. Once `colonna` is dropped, that data is gone; getting it back means restoring from a backup, not undoing the migration. Make sure the new column is fully verified and the code path is solid before you run it.
