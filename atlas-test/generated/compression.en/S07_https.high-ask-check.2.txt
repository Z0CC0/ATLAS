When you visit an HTTPS site, you're using ordinary HTTP, just run inside a channel that TLS encrypts.

It starts with your browser opening a connection and telling the server which TLS versions and cipher suites it can support. The server picks one of those versions and ciphers, then sends back its certificate. That certificate binds a domain name to a public key, and it's signed by a certificate authority. Your browser checks that signature by walking a chain of trust upward until it reaches a root certificate it already has stored — that's what makes it trustworthy without you ever having met the site before.

Note what the certificate does *not* tell you: nothing about who actually runs the site. It only proves that whoever controls that domain also controls the matching private key.

Once the certificate checks out, client and server negotiate a session key — nowadays typically via an elliptic curve Diffie-Hellman exchange. This session key is symmetric, not asymmetric, because asymmetric crypto is too computationally expensive to use for all the actual traffic; it's really only practical for the handshake itself.

From that point on, everything sent between you and the server is encrypted and authenticated with that session key. That means anyone sitting in the middle of the connection can't read it and can't tamper with it either.

One more practical detail: TLS 1.3 does all of this in a single round trip, versus two round trips in TLS 1.2 — so the newer version gets you to a secure connection faster.
