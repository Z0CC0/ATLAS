# Dart and Flutter

## The language

Sound null safety, used: nullable types only where absence is real; promotion through
checks and patterns in place of `!`. `late` only when initialisation truly cannot happen
in the constructor; a `late` that is read before it is set is a crash.
`final` by default; `const` constructors and values wherever possible.
Sealed classes for closed sets of states and results, with exhaustive `switch`. Records
and patterns for small groupings and destructuring.
Immutable data classes with `copyWith`, written by hand or generated by the project's
code generator.
Typed exceptions, caught specifically; a result type for expected failures when the
project has one. `Future`s awaited or deliberately marked unawaited.
The analyzer's lints at the level the project sets; `dart format` decides layout.

## Async

`async`/`await`; independent futures started together and awaited with `Future.wait`.
Stream subscriptions, controllers, timers and animation controllers are cancelled or
disposed by whoever created them.
After an `await` in a widget, check `mounted` before using the `BuildContext`: the widget
may be gone.
Heavy computation off the UI isolate.

## Widgets

Small widgets as classes, not helper methods returning widgets: a class gets its own
element, can be `const`, and rebuilds alone.
`const` wherever the constructor allows: it is the cheapest optimisation there is.
`build` is pure and cheap: no I/O, no creating controllers, no sorting large lists.
State as low in the tree as it can live; rebuild scope kept small with selectors,
`ValueListenableBuilder` or the state library's equivalents.
Lists through the builder constructors; keys on items that move.
Layout by constraints: flexible widgets and `LayoutBuilder` over fixed sizes; text scale
and small screens checked.
Theme values (`Theme.of`, colour scheme, text theme) in place of literals.

## State management

The one the project uses, and only that one. Common shapes:
BLoC or Cubit: events in, immutable states out; one bloc per feature; no UI code in it;
listeners for one-off effects such as navigation or a snackbar.
Riverpod: providers as the units of state and dependency; `ref.watch` in build,
`ref.read` in callbacks; notifiers hold the logic; auto-dispose for screen-scoped state.
Either way: the UI renders state and sends intents; rules, I/O and mapping live below it.

## Structure

By feature, each with presentation, logic and data; shared code apart. Repositories hide
where data comes from; models from the network are mapped to the app's own types at the
boundary, so an API change does not ripple through widgets.
Navigation declarative, with typed routes when the router supports them; redirects for
authentication in one place.
HTTP through one configured client with timeouts and interceptors for auth and errors.
Secrets and tokens in secure storage, never in shared preferences or the source.
Strings localised through the generated localisations.

## Platform

Platform channels and plugins wrapped behind an interface. Permissions asked when needed,
with the denied case handled. Tested on both platforms and in release mode: performance
in debug mode says nothing.
